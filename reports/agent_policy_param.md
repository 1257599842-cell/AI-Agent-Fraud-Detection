# `policy_param`：把成本假设升为一等公民事实

> **这条改动是 owner 人工核验 17 条时发现的**，不是代码扫出来的。
> 值得单独记一笔的原因：**外包标注找不到这个问题**——发现它需要同时知道
> ① Agent 的 system prompt 里写了什么、② 硬层数字对账器的白名单里有什么。
> 这两样都不在标注表上，只有真正把系统读通的人才会撞见。

## 问题：两层对「证据」的定义不一致

owner 在唯一那条 `reasoning_valid=false`（`3510638#0`）的批注里写：

> 「『误伤成本>损失』需成本数据支撑，证据池缺失该类证据，属非因果跳跃。
> **但之前在 ml 层确实有过类似的结论，因此我怀疑是不是需要结合更大背景比如整个项目的。**」

核实后确认**这不是他判错，是系统本身矛盾**：

| | 成本推论（如「误伤成本 > 潜在损失」） |
|---|---|
| **Agent 的 system prompt** | 明写着「误拦 $25 / 挂起复核 $5 / 上报建档 $40」 |
| **硬层数字对账器** | `COST_CONSTS` 早已把这些常数当作**合法来源**，引用它们不算编造 |
| **软层 RUBRIC_V2** | 要求「只依据给出的证据判断」，而**证据池里没有这些常数** |

→ **同一个成本推论，硬层判它有据、软层判它无据。**

## 拍板：往严统一（新增 `type: policy_param`）

把成本假设**登记为事实**，进事实登记表，要求被引用。

**为什么不反向做**（把 `COST_CONSTS` 从硬层白名单剔除）：
- (a) 那会给**站得住的推理**制造假的引用缺失；
- (b) 一份推荐意见所依赖的假设，本就该出现在**审计链**上——
  而它们恰好就是敏感性扫描里被扫的那几个参数（D 已证一致率随它们摆 15 个百分点）。

## 实现

```python
# src/agent/tools.py
POLICY_PARAM_TYPE = "policy_param"
policy_facts(registry, params)   # → POLICY_000..005，进 FactRegistry
```

**时间窗的处理**：`policy_param` 不是观测，是**假设**，没有时间窗。
记为 `window=(0,0)`、`label_based=False`——语义是「先于全部数据即已知」，
于是 `audit_time_boundary` **天然放行，不需要为它开任何豁免口子**。
（开豁免＝给自己留后门；本项目已经在「静默放行」上栽过三次。）

## 结构性修法：三处指向同一份定义

真正的病根不是「少了一类 fact」，是**同一组常数被写了三遍**：
四档公式的 `BASE`、prompt 里的文本、硬层的 `COST_CONSTS`——三份可以各自漂移。

现在 `COST_CONSTS` **从 `disposition.BASE` 派生，不再手抄**。

### 派生时踩到的坑（记下来，因为它正是本项目反复强调的那类错误）

首版派生把 `POLICY_DESC` 里**全部** 6 个参数都放进白名单，结果
`fully_cited` 从 **522 涨到 523** ——「硬层数字不变」这个前提被我自己的实现打破了。

查因：`m_h` / `m_e` / `k_future` 虽然也是 policy_param，但**从未出现在 Agent 看得到的任何地方**
（prompt 只写了 $25/$5/$40）。把它们列入白名单 = **给 Agent 没见过的数字发通行证**，
那是放宽而不是统一。另外 `m_h=0.10` 的百分数形态是 `10.0`，这种泛数会顺带放行大量无关匹配。

收紧为「只收 prompt 里真的告诉过 Agent 的三个」之后：

| | 旧硬编码 | 新派生 |
|---|---|---|
| 白名单 | `{3.5, 0.035, 25, 5, 40, 21}` | `{3.51, 0.0351, 25, 5, 40, 21}` |
| `fully_cited` | 522 | **522** |
| `citation_gap` | 43 | **43** |
| `true_ungrounded` | 0 | **0** |

唯一差异是基率写法 `3.5 → 3.51`（`BASE_RATE=0.0351` 的**正确**百分数形态，旧值是四舍五入近似），
结果逐项不变。**「硬层数字不变」是验证出来的，不是假设的。**

## 影响范围

- **不需要重跑**：硬层数字逐项不变（上表），软层已退役。
- **不改 Agent 看到的东西**：本轮只改定义、登记表与文档。
  把 `policy_param` **surface 给 Agent**（让它能真的去引用）是**另一次改动**，
  需要单独一轮——否则会和 round 4 的 prompt 改动混在一起，
  主指标会因「不再全是 `txn_field`」而下降，那不是 prompt 的功劳。
  **一次只改一处**，round 3 的教训。

## 一句话结论（可对外）

> 「人工核验发现了一个架构级不一致：同一个成本推论，硬层判有据、软层判无据。
> 修法是把成本假设升为一等公民事实进审计链，并让三处配置从同一份定义派生——
> 顺带发现我自己的第一版派生偷偷放宽了白名单，靠『旧结果必须逐项不变』这条回归校验抓了回来。」
